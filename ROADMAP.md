# Omni Roadmap — Sequenced by Risk and Value

Written 2026-11-23. Consolidates the decisions from the AI-first-language
debate (Response #002 Omni-S, Response #003 caps critique, the 1.0 Spec,
`counter.md`, and Response #005's counter to the counter) into a single
ordered plan. The debate has converged; this is what was settled.

## Settled principles

These are no longer open questions. They constrain everything below.

1. **Trusted vs. untrusted boundary.** The verifier (`pure/verifier_engine.omni`,
   per-function checks) is the trusted computing base and stays isolated.
   All authoring ergonomics — the elaborator, the CFG grammar, the repair
   loop — live in untrusted frontends. A bug in an untrusted layer can only
   cause a static rejection, never a bypass. This is the single most
   important architectural decision, and all three AIs agree on it.

2. **Audit view is a hard gate.** Before the proposer loop auto-commits
   token streams, a deterministic decompiler must exist: M3-shaped text
   AND a plain-language summary, in the same step. The summary is
   generated by **deterministic templates from static capability, taint,
   and sink metadata — never by an LLM**, which can hallucinate benign
   intent over unsafe capability flows. (Response #005's correction,
   adopted.)

3. **Risk-ordered sequencing.** Work is ordered by risk profile, not by
   enthusiasm. Cheap de-risking first, high-value builds second, verifier
   changes last and only on evidence. A roadmap item is not a commitment
   to build it; it is a commitment to build it *in this order, when its
   turn comes*.

4. **Caps: the middle path.** The choice is not "keep the exact ceilings"
   versus "build a call-graph analyzer." Raising a constant — more labels
   per function, two bytes parameters instead of one — is still
   per-function, still O(N), still decidable. It needs no cross-function
   inference. That middle path is real. But the evidence bar stands: raise
   a constant only when a real program hits it and cannot be restructured,
   and then raise just that constant, with a gate, because seeds and
   hashes move. (Response #005's correction, adopted.)

5. **Outlining has real costs.** The elaborator avoids local caps by
   outlining logic into helper functions, but that costs call frames
   (64-frame call-depth ceiling) and buffer-packing overhead. The
   existing corpus was hand-authored around the caps, so "nothing has
   hit them" is survivorship bias, not proof. The elaborator must
   therefore outline *shallowly* (sibling helpers called in sequence,
   not deep nesting) and pack buffers by *offsets into one arena handle*
   (references, not copies), not by copying data or spilling through
   host_kv. Multi-buffer operations are handled by offset-based packing
   first; relaxing the bytes-parameter lint rule is the fallback if a
   real program shows packing is too costly. (Response #005's correction,
   adopted in part.)

6. **Blobs are a tradeoff, and the gates already catch desync.** The six
   checked-in `.omni_bc` binaries exist to bootstrap the chain quickly.
   A hash-keyed local/CI build cache (keyed by source hash, excluded from
   Git) is a reasonable alternative, but it is more infrastructure for a
   problem the gates already catch: S3.1 verifies the standalone seeds
   match source with zero-word diff, and the fixed points verify the
   rest. Desync is not silent in practice. Blob elimination is low
   priority, not a 1.0 item. (Response #005's point acknowledged; the
   urgency is not accepted.)

### 1 — Seventh benchmark for M3

The corpus stops at 7. Add the seventh benchmark (an M3-frontend
workload), then the M3 frontend flywheel pass. This is the already-decided
next work after the bench PR #17 landed. Do not change the judge
mid-flywheel; do not add emitter squeezes.

### 2 — CFG grammar + structured error schema

Cheap to define, de-risks everything that follows, reusable by the
proposer loop regardless of what comes after. A prefix S-expression
grammar enforceable by a token mask at sampling time (eliminates syntax
errors before the compiler runs), plus a machine-readable error-repair
schema (exact location, quantitative headroom, structured deltas) so the
M7 repair loop converges instead of guessing. This is the most actionable
single improvement in the whole debate.

### 3 — Elaborator (Omni-S) + M7 wiring

The big build and the highest-value work. A Pure-Omni elaborator under
`pure/script/` that lowers an AI-first surface language (.omnis) into
standard Omni IR ahead of `pure/m3/lower.omni` and
`pure/verifier_engine.omni`, keeping core Omni untouched as the
verifiable kernel. The elaborator automates the mechanical burden the
caps impose (arena/linear/capability boilerplate, buffer threading,
fragmentation) — it is the answer to the authoring friction, not
relaxing the caps. Wired to the structured error schema and the M7
proposer/heal loop so failures converge in one shot. Design constraints
from principle 5: outline shallowly, pack buffers by offsets.

### 4 — Audit view (M3 text + deterministic summary)

Must land **before** the proposer loop starts auto-committing token
streams. The decompiler turns a token stream back into M3-shaped text
plus a plain-language summary, both in the same step. The summary is
deterministic templates from static metadata (principle 2). This is the
necessary counterpart to zero human readability: without it, nobody can
audit, debug, or trust what the AI built.

### 5 — Proposer loop

The measurement loop (P7-0: benchmark corpus + timing/size + adopt/reject
rule) already exists in design; build the proposer itself, with the
automated verification pipeline (CI + Linux verification) as the merge
gate. Caleb's decision stands: 100% AI-maintainable, +1t ADOPT
auto-commits to a dedicated branch, no human merge. The merge gate must
be automated — an auto-merge without an automated Linux check repeats
the Round 2 failure mode.

### 6 — Phase 2a: syscall intrinsics (literal zero Rust)

Remove Rust from the build path: syscall intrinsics in the M2 emitter
plus a tiny assembly entry stub. The no-Rust chain is already proven
(m2.elf rebuilds itself byte-for-byte with no Rust process running).
Sequenced after the proposer loop. Open decision: keep the Rust code as
a permanent differential-testing reference (pinned toolchain) or delete
it for literal zero Rust. Cheapest high-value step in the meantime: a CI
job running the proven no-Rust chain against the pins.

### 7 — Accelerator (after P7-3)

Extend `spec/heterogeneous_design.md` (it already exists as a design-only
spec) with the ONNX Runtime dispatch section and the determinism guardrail
as a hard rule: tensor ops are a host capability with a pure-Omni software
fallback; the accelerator is an optimization, never a dependency; the
tensor path lives outside the deterministic core (gates and frozen hashes
never depend on accelerator bits); never in the compile/verify loop.
Then one tensor op (TDOT recommended) behind `#[cap(AI)]`, CPU fallback
byte-identical. Dispatch to the Z13's XDNA NPU (~50 TOPS) or iGPU locally;
cloud TPU via XLA only as a rental.

### 8 — Arena consolidation + std/ expansion (maintenance)

Unify the duplicated arena implementations and expand `std/` (bounded
slices, string/byte utilities, error-propagation combinators). Useful,
low-risk, and can proceed in parallel with the above when convenient.
Not a gating item.

## Deferred — only if a real program demands it

- **Whole-call-graph resource envelopes.** A verifier redesign and a
  research project, not a 1.0 item. The bar: a real program that hits a
  cap and cannot be restructured around it. Until then, the middle path
  (principle 4) is how caps move.
- **Blob elimination.** See principle 6. Low priority.
- **ARM64 native emitter + lightweight LSP.** Useful tooling, not the
  bottleneck. M4 VM + Wasm already work on ARM64.

## What the other AIs got right (kept)

- The elaborator is the right answer to authoring friction.
- CFG-constrained decoding is a genuine win.
- Structured counterexamples into M7 is the most actionable improvement.
- Expanding `std/` is genuinely useful and low-risk.
- De Bruijn slots fix a real failure mode (naming drift, shadowing).

## What was rejected (and why)

- **"The caps are the biggest issue."** No demonstrated victim; caps are
  per-function/per-module, not per-program; the elaborator (not relaxing
  the caps) is the answer to the friction.
- **Call-graph budgets as a near-term item.** Much harder verification
  problem, high risk to the trusted base, no demonstrated need.
- **Bundling five items as one "1.0".** Different risk profiles; they
  are a roadmap, not one step.
- **LLM-narrated audit summaries.** Deterministic templates only
  (principle 2).

## Open decisions (not settled by this roadmap)

- Rust-removal oracle: keep Rust as a permanent differential-testing
  reference vs. delete it for literal zero Rust.
- The exact seventh benchmark workload.
- Whether the hash-keyed build cache replaces the checked-in blobs
  (low priority either way).
